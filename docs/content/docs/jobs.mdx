The `jobs` module adds `packages/jobs`: queues, retries and cron on top of the Postgres you already run, through [pg-boss](https://github.com/timgit/pg-boss). No Redis. It is off by default.

```bash
findplate create my-app --modules jobs
```

pg-boss keeps its own `pgboss` schema in the same database and creates or migrates it when the api starts, so there is no drizzle migration to generate.

## Define a job

A job is a queue name, a zod payload and a handler. Put it in `packages/jobs/src/jobs/` and add it to `JOBS` in `packages/jobs/src/jobs/index.ts`.

```ts
export const welcome = defineJob({
  name: "send-welcome",
  description: "Welcome mail after sign up",
  payload: z.object({ userId: z.string() }),
  retry: { limit: 5, delaySeconds: 30, backoff: true },
  handler: async ({ userId }, { db }) => {
    // db is the same drizzle instance the api uses
  },
})
```

Enqueue it from the api with the typed `send`, the payload is checked at compile time and again at runtime:

```ts
await services.jobs.send(welcome, { userId })
```

`retry` is `limit` extra attempts after the first failure, waiting `delaySeconds`, doubled each time when `backoff` is on. A job that keeps failing stays visible as `failed` in the admin list. The default is 3 retries from 30 seconds with backoff.

## Cron

Add `cron` and `scheduleData` to a definition and the worker registers the schedule on start (cron expressions are evaluated in UTC):

```ts
defineJob({ name: "digest", cron: "0 8 * * 1", scheduleData: {}, ... })
```

The sample `cleanup-sessions` job runs every night at 03:00 and deletes expired sessions. `echo` has a payload and no side effect, handy to see the worker run. Removing a job from the code does not remove its schedule from the database, run `delete from pgboss.schedule where name = '<job>'` once.

## Admin procedures

Admins only, also reachable over REST under `/v1`:

| Procedure | What it does |
| --- | --- |
| `jobs.list` | every job with its cron and queued, active and failed counts |
| `jobs.enqueue` | `{ name, payload }`, checks the payload against the job's schema and answers `BAD_REQUEST` when it doesn't fit |

## Running the worker

By default the api process runs the worker and the cron scheduler itself, which is right for one container and for local dev. To scale or isolate them, turn it off on the api and run the worker apart:

```bash
JOBS_WORKER=false   # on the api, it then only enqueues
```

- locally: `pnpm dev:worker`
- anywhere: `bun apps/api/src/worker.ts`
- Docker: the api Dockerfile has a `worker` target, `docker build --target worker -f apps/api/Dockerfile .`. It is the same image without the http server and the health check.
- Dokploy: add a second application from the same repo, set the Dockerfile to `apps/api/Dockerfile`, the build target to `worker`, and give it the same env as the api. It exposes no port, so skip the domain.

Run as many workers as you like, pg-boss hands each job to one of them and runs each cron tick once.

## Run on trigger.dev

pg-boss needs no extra service, which is why it is the default. If you would rather have a dashboard, long running tasks and no worker to operate, add the `trigger` module (it needs `jobs`):

```bash
findplate add trigger
```

The jobs stay the same typed `defineJob` definitions. Each one also becomes a trigger.dev task in `packages/jobs/src/trigger/tasks.ts`, with the job name as task id, its retry policy and, for cron jobs, a declarative schedule. A new job needs its line there as well as in `JOBS`, a test fails when one is missing.

Set the key and the api enqueues to trigger.dev instead of pg-boss, leave it empty and nothing changes:

```bash
TRIGGER_SECRET_KEY=tr_dev_...   # from cloud.trigger.dev, or your own instance
TRIGGER_API_URL=                # only for a self-hosted instance
TRIGGER_PROJECT_REF=proj_...    # for deploys
```

- `pnpm trigger:dev` runs the tasks locally against your dev environment
- `pnpm trigger:deploy` deploys them. Set `DATABASE_URL` in the project's environment variables on trigger.dev, the handlers use the same database as the api
- `jobs.list` counts runs from the trigger.dev api (up to 100 per status), `jobs.enqueue` triggers the task
- `JOBS_WORKER` does nothing then, trigger.dev runs the handlers

Self hosting: trigger.dev v4 is open source, follow its [self-hosting guide](https://trigger.dev/docs/self-hosting/overview) (docker compose, or Kubernetes) and set `TRIGGER_API_URL` to it. It is a bigger stack than the other self hosted modules (its own postgres, redis and a supervisor), so use the cloud to start.

pg-boss or trigger.dev? pg-boss when you want one less service and jobs that finish in seconds. trigger.dev for long tasks, a run dashboard, replay and fan out. [Inngest](https://www.inngest.com) and [Hatchet](https://hatchet.run) fit the same slot if you prefer them, the `Jobs` interface in `packages/jobs/src/index.ts` is what the api needs.

## Graceful shutdown

On `SIGTERM` or `SIGINT` the api stops accepting requests, waits up to 8 seconds for running jobs to finish and exits, which fits the 10 seconds Docker gives a container. Jobs still running after that are failed and retried by another worker, so write handlers that are safe to run twice.
